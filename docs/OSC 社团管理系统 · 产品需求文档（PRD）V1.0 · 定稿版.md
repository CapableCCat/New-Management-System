## 第零步：总纲（三个问题的回答）

### Q1 · 产品定义（双层结构）

**V1.0 层（本次交付）** ：在开学纳新窗口期，为「扫码报名的新生」与「社团管理成员」提供一套**手机/PC 双端、分辨率适配良好、稳定运行**的"报名 → 审核 → 成员管理"闭环，使纳新结束即获得一份完整的数字化成员名册与招新过程数据。

**中期层（架构愿景，V2.0，V1.0 不做）** ：系统演进为社团的"数字资产库"——对社团内部资产（虚拟/硬件实体）、荣誉、活动、报表进行结构化归档与备份。

**长期层（优化远景，V3.0）** ：在传统系统稳定后，引入 **RAG + 本地部署小模型**实现智能化检索，取代"靠记忆翻文件"的旧方式。

### Q2 · 上线观测指标（社团语境）

社团非商业组织，**不存在层级与转化率 KPI，纳新采用统一评审**，审核时效难以量化，故指标改为"过程观测值"而非考核指标：

- **报名过程记录**：扫码访问数 → 提交报名数 → 评审通过数 → 登录激活数（按日归档，用于复盘，不设目标值）
- **成员画像分布**：通过成员按学院/专业/性别/地区统计，辅助后续活动组织
- **稳定性硬指标**：纳新期内 0 次不可恢复故障、0 数据丢失
- **反馈回收**：收集 ≥20 条新生/管理成员真实反馈（支撑 V1.5 迭代与毕设数据）

## 一、背景与目标（Why）

### 1.1 现状

旧系统为社长自学迭代产物（Vue 2 + Spring Boot 半成品），功能大多失效、仅能 mock 演示。代码层面存在鉴权冲突、密码明文、配置硬编码、大量业务校验被注释等问题。

### 1.2 驱动力

纳新需要真实上线且稳定的初版；同时将实习所学"用户/产品视角"落地为一次真实的"上线 → 收数据 → 复盘 → 迭代"循环。

### 1.3 系统定位声明

**系统不与飞书竞争日常协作。** 飞书管"今天"，OSC 管"昨天和明天"——定位为社团数字资产库与流程引擎。

- **飞书**：日常沟通、填表、传文件（数据产生于此）
- **OSC 系统**：查询历史、导出报表、换届交接（数据归档于此）
- **社团官网**：对外展示门面（内容呈现于此）

系统**不增加日常录入负担**，只接收"整理过的数据包"与"关键节点快照"。运营同学日常不需要打开系统，每学期导入 1~2 次飞书导出的 Excel 即可。

### 1.4 V1.0 非目标（明确不做）

不做 IM/聊天、不做飞书数据自动同步、不做活动报名签到、不做资产借还台账、不做 AI 检索、不做官网门户。

## 四、功能需求详述

### F-001 公开报名页

**优先级**：Must ｜ **所属切片**：V1.0 第 1 片

**用户故事**：作为新生，我在摊位扫码后用 ≤3 分钟完成报名，提交后能知道"何时有结果、去哪查"。

**功能描述**：
- **入口**：扫描摊位二维码/点击群内链接，直接打开报名页（无需登录）
- **主要流程**：
  1. 展示社团简介（Logo、一句话介绍、活动照片轮播）
  2. 填写报名表单：姓名（必填）、手机号（必填）、学院（必填，字典）、专业（必填，字典+其他兜底）、意向部门（可多选，字典）、兴趣标签（多选，字典）、性别（选填）、生源地省市（选填，级联）
  3. 勾选隐私说明（"你的信息仅用于社团联络与纳新审核"）
  4. 提交 → 系统校验手机号是否已报名（重复则提示"你已提交过报名，请勿重复提交"）
  5. 提交成功 → 展示成功页："报名已提交，预计1~2个工作日内完成审核。你可以凭手机号在[状态查询页]查询结果。"
- **分支与异常**：
  - 手机号格式错误 → 实时提示
  - 手机号已存在报名记录（待审/已通过）→ 提示已提交，引导去查询页
  - 手机号已存在报名记录且状态为**已拒绝** → 允许重新提交（更新原记录，状态重置为待审）
  - 网络失败 → 提示重试，保留已填内容

**验收标准**：
- [ ] 新生在手机端 3 分钟内可完成报名并看到成功页
- [ ] 同一手机号重复提交时，提示"已提交过报名"并引导至查询页
- [ ] 被拒绝者可重新提交报名（更新原记录，状态重置为待审）
- [ ] 提交成功页明确告知审核时效和查询方式
- [ ] 隐私说明在提交前可见

**数据要求**：
- 写入 `recruit_apply` 表：`name`, `phone`, `college`, `major`, `intent_departments`, `tags`, `gender`, `province`, `city`, `status`（默认待审）, `created_at`
- 手机号唯一约束（`UNIQUE`）
- 学院/专业/意向部门/兴趣标签来源：`sys_dict` 表
- `tags`（兴趣标签）与 `intent_departments`（意向部门）的存储格式（JSON 数组或关联表）由技术方案确定，建议 JSON 数组

**关联**：F-011（字典管理）、F-005（状态查询页）


### F-002 手机号+密码登录

**优先级**：Must ｜ **所属切片**：V1.0 第 2 片

**用户故事**：作为已激活的成员，我用手机号和密码登录系统，查看公告和个人信息。

**功能描述**：
- **入口**：系统首页 → 登录页
- **主要流程**：
  1. 输入手机号 + 密码 + 图形验证码
  2. 系统校验：验证码正确 → 查询 `user` 表手机号 → BCrypt 比对密码 → 检查账号状态（正常/冻结）
  3. **首次登录判定**：若 `activated_at` 为空（尚未首登）→ 强制跳转改密页，改密成功后才可进入系统（同步写入 `activated_at`）
  4. 登录成功 → 生成 Sa-Token（Header 方式返回）→ 前端存储 → 跳转首页
- **分支与异常**：
  - 验证码错误 → 提示"验证码错误"，刷新验证码
  - 手机号不存在 → 提示"账号不存在，请确认手机号或先提交报名"
  - 密码错误 → 提示"密码错误"，累计失败次数
  - 连续失败 5 次 → 锁定 15 分钟，提示"尝试次数过多，请15分钟后重试"
  - 账号冻结（已离社）→ 提示"账号已冻结，请联系管理员"
- **忘记密码**：登录页底部显示"忘记密码？请联系管理员重置"。管理员后台提供"重置密码"功能，生成随机密码后通过短信提效工具发送给用户。

**验收标准**：
- [ ] 正确手机号+密码+验证码可登录
- [ ] 首次登录（初始密码）强制修改密码，改密成功前不可访问其他页面
- [ ] 密码错误 5 次后锁定 15 分钟
- [ ] 冻结账号无法登录并提示联系管理员
- [ ] 登录成功后 Token 通过 Header 返回，前端持久化

**数据要求**：
- 读取 `user` 表：`phone`, `password`(BCrypt), `status`, `activated_at`
- 密码使用 BCrypt 加密存储
- 登录失败次数记录在 Redis（key: `login:fail:{phone}`，TTL 15min）
- `activated_at`：首次登录并完成强制改密后写入（为空=未首登）

**关联**：F-003（审核通过后建账号）


### F-003 审核管理台

**优先级**：Must ｜ **所属切片**：V1.0 第 3 片

**用户故事**：作为管理成员，我在纳新期集中评审报名，能一次看到全部申请、快速通过/拒绝并留痕，且通过后新生"马上能登录"。

**功能描述**：
- **入口**：管理端 → 审核管理台（需登录且有权限）
- **主要流程**：
  1. 展示报名列表：姓名、手机号、学院、专业、意向部门、兴趣标签、提交时间、状态
  2. 支持筛选：按状态（待审/通过/拒绝）、按学院、按意向部门、按提交时间
  3. **评审范围（数据隔离）**：社长团/超管可评审全部报名；**部长仅可评审"意向部门包含本部门"的报名记录**
  4. **通过操作**：点击"通过" → 系统自动创建 `user` 账号（手机号为主键，初始密码随机生成）→ 弹窗展示初始密码 → 提示"请通过短信通知该成员"
  5. **拒绝操作**：点击"拒绝" → 弹出输入框，**必须填写拒绝原因**（提示：该原因将展示给被拒者，请使用可对外措辞）→ 提交后更新 `recruit_apply.status=拒绝`，记录拒绝原因、审核人、审核时间
  6. **批量操作**：支持多选待审记录，批量通过（批量通过时密码逐条生成，可一次性导出密码清单）
- **分支与异常**：
  - 审核通过时账号创建失败（手机号冲突）→ 提示"该手机号已存在账号，请检查"
  - 拒绝时未填原因 → 提示"请填写拒绝原因"
- **审核人留痕**：每条审核记录保存 `reviewer_id`、`reviewed_at`

**验收标准**：
- [ ] 通过后自动创建用户账号，弹窗展示初始密码
- [ ] 拒绝时必须填写原因，否则无法提交
- [ ] 审核人和审核时间被记录
- [ ] 支持批量通过，可导出密码清单
- [ ] 部长只能看到"意向部门包含本部门"的报名记录（数据隔离）

**数据要求**：
- 读取 `recruit_apply` 表
- 写入 `user` 表（通过时）：`phone`, `password`(BCrypt), `status=0`, `activated_at=null`
- 更新 `recruit_apply`：`status`, `reject_reason`, `reviewer_id`, `reviewed_at`

**关联**：F-001（报名页）、F-004（短信工具）


### F-004 短信通知提效工具

**优先级**：Must ｜ **所属切片**：V1.0 第 4 片

**用户故事**：作为管理成员，我想快速复制审核结果和新生手机号，用自己的手机发送短信通知，避免手打。

**功能描述**：
- **定位**：系统**不代付**短信费用，仅提供操作提效工具，复用干部个人手机短信能力。
- **单个发送**：
  - 审核通过/拒绝后，弹窗显示"复制通知话术"按钮
  - 点击后系统自动拼接短信内容（模板+系统链接）并复制到剪贴板
  - 干部粘贴到短信 App 发送

### 6.1 账号三标识

| 标识符       | 唯一性     | 必填/可空                    | 用途                       |
| :----------- | :--------- | :--------------------------- | :------------------------- |
| 手机号       | ✅ 全局唯一 | **必填**                     | 登录主键；纳新报名唯一标识 |

### 6.2 权限字段设计

> 对应第五章"角色资格推导"，明确"超管/社长团/部长"在数据上如何标识与推导。

- `user.role`（TINYINT）：0=普通成员、2=超管（沿用旧系统编码习惯；旧的 1=管理员 不再使用，迁移时按部门/职位重新映射）
- 全社管理资格：`department = 0`（社长团）
- 部门管理资格：`duty = 2`（部长），数据范围为本人所在部门
- 评审报名范围：社长团/超管=全部；部长=意向部门包含其所在部门的报名（见 F-003）
- 权限判定以后端校验为准，前端仅控制可见性

### 6.3 报名与账号两阶段

| 表              | 职责                                                  | 状态字段                             |
| :-------------- | :---------------------------------------------------- | :----------------------------------- |
| `recruit_apply` | 纳新季**全量报名记录库**                              | `待审 / 通过 / 拒绝`（含拒绝原因）   |
| `user`          | **正式社团成员库**（仅存审核通过的成员，含本届+往届） | `正常 / 冻结`（封禁/已离社共用冻结） |

**数据流向**：
1. 新生填报名表 → `recruit_apply` 新增记录，`status=待审`
2. 干部审核通过 → `recruit_apply.status=通过` + `user` 表插入账号记录（手机号为主键，初始随机密码）
3. 干部审核拒绝 → `recruit_apply.status=拒绝`，不创建账号

**成员列表查询**：只展示 `user` 表数据。报名表数据仅在审核台和查询页展示。

## 七、非功能需求（NFR）

1. **移动端适配（最高优先级）** ：报名页、状态查询页、审核列表页以移动端为第一体验。不依赖 hover、大表格等桌面交互。
2. **性能**：纳新峰值预估 50~200 并发；报名提交幂等 + 弱网重试；首屏耗时 ≤3 秒。
3. **安全**：
   - 密码 BCrypt 加密存储
   - 登录图形验证码防爆破（非短信）
   - 连续失败 5 次锁定 15 分钟
   - 富文本 XSS 清洗（前后端双重）
   - 越权防护以后端校验为准
   - 敏感字段分级可见
   - 短信模板中链接为配置项，不硬编码
4. **稳定性与数据**：
   - 报名/审核关键操作不丢数据
   - 数据库每日备份（纳新期必做）
   - 关键操作留痕（审核人/时间）
5. **合规**：
   - 个人信息最小化收集（手机号/学院等）
   - 报名页隐私说明
   - 不采集身份证
6. **部署与访问**：
   - 纳新期需公网或现场可达（手机访问）
   - 公网 HTTPS 同时是飞书免登/Webhook 前置条件
7. **可维护性**：
   - 字典外置
   - 配置环境变量化
   - 日志规范
   - 为 V1.5 平滑扩展预留

## 附录 D：关键决策溯源记录

> **文档性质**：本附录记录最终PRD中各关键决策背后的**理由**。正文只写"怎么做"，本附录回答"当初为什么这么定"，供未来迭代时理解设计意图。
> **使用方式**：开发中若对某决策有疑问，先查本附录；若理由已不成立，再讨论修订。

---

### D-1 登录通道：为什么飞书免登降为Stretch Goal

**决策**：V1.0以"手机号+密码+图形验证码"为主通道；飞书OAuth2.0免登为条件项（需公网HTTPS + 飞书应用审批通过）。

**理由**：
1. **免登覆盖不了纳新主场景**：免登前提是用户已在飞书组织内，而纳新对象是校外新生，根本不在组织里，走不了免登。
2. **公网HTTPS是硬前置**：飞书自建应用回调要求公网HTTPS，与旧系统内网IP部署是同一个坑。公网一天不解决，免登一天做不了。
3. **账密通道才是生死线**：新生报名→审核→激活→登录，全链路必须能走通，这条链不能依赖"条件项"。

---

### D-2 审核通知：为什么是"干部自费短信+提效工具"

**决策**：系统不代付短信费用，仅提供"复制话术+号码"和"批量复制+统一话术"两个提效工具；同时提供公开状态查询页作为兜底。

**理由**：
1. **新生不在飞书群里**：Webhook推不到报名新生，只推给干部群。
2. **状态查询页依赖主动刷新**：新生不会没事刷系统，等不到结果可能对系统产生负面情绪（尤其被拒者）。
3. **短信是低频关键场景最可靠的触达**：但申请短信网关要流程、要付费，学生社团不现实。
4. **干部用自己的手机发**：内容一样，但"真人发来的"比"机器通知"更有温度；系统只做提效，不碰钱，合规无风险。

---

### D-3 报名与注册解耦：为什么报名不建账号

**决策**：报名阶段只创建`recruit_apply`记录（不建账号、不设密码）；审核通过时才自动创建`user`账号。

**理由**：
1. **安全**：报名阶段允许设密码，会导致无短信验证的手机号注册面临刷号/冒用风险。
2. **干净**：未通过审核的手机号不产生垃圾账号。
3. **自然解决"新生没学号"**：审核通过后才激活账号，学号此时可为空，登录后补录。

---

### D-4 账号三标识：为什么是手机号主键

**决策**：手机号（登录主键，唯一必填）；学号（唯一可空，自助补录）；飞书open_id（唯一可空，绑定）。

**理由**：
1. **手机号是纳新现场唯一可确认的真实联系方式**：新生报名时不一定知道学号，强制填写会流失报名。
2. **学号是教育体系关联标识**：用于学校对接、评优验证，但不应作为登录凭据（会变、会没有）。
3. **飞书open_id是三方绑定标识**：只在免登场景下使用，可空。

---

### D-5 审核状态归属：为什么只在报名表维护

**决策**：审核状态（待审/通过/拒绝）**只在`recruit_apply`表维护**；`user`表只管账号生命周期（正常/冻结）。

**理由**：
1. **两个表职责完全不同**：报名表管"纳新事件的进度"，用户表管"这个人能不能登录系统"。
2. **报名人数远超纳新人数**：报名表是全量记录库，用户表只存正式成员。拒绝者不应进入用户表。
3. **单一数据源**：审核状态只有一处，改状态时不会出现"两表忘同步"的bug。
4. **数据流向清晰**：报名→待审；通过→写入user；拒绝→只留报名记录。

---

### D-6 输入方案：为什么不做飞书API自动拉取

**决策**：V1.0不做任何自动化数据拉取，改用"飞书导出Excel→系统导入"半自动模式 + "快记面板"轻量录入。

**理由**：
1. **飞书API拉取通讯录/多维表需付费版本**：免费版不支持，学生社团无法承担。
2. **权限审批复杂**：企业自建应用需管理员授权，流程长。
3. **数据映射易出错**：飞书字段与系统字段的映射维护成本高。
4. **半自动方案质量更高**：数据经人工整理后导入，比自动拉取的脏数据更干净。
5. **使用门槛极低**：运营同学每学期只需导入1次，不增加日常负担。

---

### D-7 部长审核权：为什么部长可审核本部门

**决策**：部长可审核本部门的报名；社长团可审核全部。

**理由**：
1. **部长最了解本部门需要什么样的人**：纳新本质是"为自己挑选合适的人选"。
2. **分散评审压力**：避免评审集中在少数人手里造成积压。
3. **数据隔离已有基础**：成员档案管理已按部门隔离，审核台复用同一套权限逻辑。
4. **实现方式**：报名表新增「意向部门（多选）」字段——新生报名时即表达部门意愿，部长按「意向部门包含本部门」过滤评审，既是数据隔离依据，也贴合真实纳新场景。

---

### D-8 忘记密码：为什么V1.0用管理员重置

**决策**：V1.0采用"联系管理员重置"；管理员后台提供重置随机密码功能 + 短信提效工具发送。

**理由**：
1. **无短信/邮箱验证通道**：自助找回需要短信或邮箱验证，V1.0两者都不具备。
2. **管理员重置成本极低**：后台加一个"重置密码"按钮即可，开发量半天。
3. **使用频率低**：纳新期用户刚拿到初始密码，忘记概率低；上线后按真实反馈再决定是否做自助找回。

---

### D-9 报名表性别/生源地：为什么保留为选填

**决策**：报名表保留"性别（选填）+ 生源地省市（选填）"。

**理由**：
1. **看板需要这两张分布图**：性别/地区分布是招新复盘的重要维度。
2. **选填不增加负担**：新生可跳过，不影响报名完成率。
3. **数据来源一致性**：看板统计口径与报名表字段对齐，避免"图上要、表里没有"的矛盾。

---

### D-10 初始密码：为什么随机生成+首登强制改密

**决策**：审核通过时自动生成随机强密码；首次登录强制修改密码。

**理由**：
1. **`OSC@+手机号后6位`可推导**：任何知道手机号的人都能猜到密码，不安全。
2. **随机密码+强制改密**：是行业标准做法，兼顾安全与可用性。
3. **干部转达成本可控**：审核弹窗展示初始密码，干部通过短信工具发给新生即可。

---

### D-11 验证码：为什么是图形而非短信

**决策**：登录用图形/算术验证码；短信不参与登录。

**理由**：
1. **短信要钱**：与"不代付短信费用"的决策一致。
2. **图形验证码足够防机器**：登录场景的威胁是脚本爆破，图形验证码+失败锁定已足够。
3. **旧系统已验证可行**：旧系统使用easy-captcha算术验证码，可用。

---

### D-12 状态查询页防探测：为什么加图形验证码

**决策**：状态查询页要求"手机号+图形验证码"。

**理由**：
1. **公开页面可被脚本批量探测**：不加验证码，攻击者可遍历手机号查询他人审核状态。
2. **图形验证码成本极低**：复用登录页的验证码组件即可。
3. **不泄露额外信息**：只返回状态和拒绝原因，不返回姓名等其他字段。

---

### D-13 字典热更新边界：为什么核心编码冻结

**决策**：字典支持增删改启停，但**核心条目（部门/职位/状态的已有编码）不可修改**，仅可改文案/排序/启停。

**理由**：
1. **业务逻辑引用稳定编码**：代码里写的是`status=0`（正常）、`duty=2`（部长），编码一变全部报错。
2. **文案可变、编码不可变**：允许改"技术部"为"Tech部"，但不允许把编码1改成别的含义。
3. **新增条目自由**：新增部门/职位/状态编码不受限制。

---

### D-14 身份证：为什么彻底删除

**决策**：不采集、不存储、不导出。

**理由**：
1. **合规风险**：学校场景收集身份证属"过度采集"，违反《个人信息保护法》最小必要原则。
2. **旧系统明文存储**：风险不可接受，不迁移。
3. **无实际必要**：纳新审核只需确认学生身份，线下核验即可。

---

### D-15 系统定位：为什么不与飞书竞争

**决策**：系统定位为"社团数字档案馆"，不做IM、不做日常协作。

**理由**：
1. **调研结论**：飞书在通用协作与审批功能上完全满足社团日常运营需求，系统在功能层面无法竞争。
2. **差异化价值**：系统回答飞书回答不了的"关联性问题"（纳新过程数据、资产台账、荣誉归档）。
3. **价值重心**：系统首先利好个人（毕设/软著/简历），其次通过"传承包"和"一键报表"间接利好社团。
4. **输入原则**：不增加日常录入负担，只接收"整理过的数据包"与"关键节点快照"。
